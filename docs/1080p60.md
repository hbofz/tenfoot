# 1080p60 on a Raspberry Pi 4 in Chromium, with the GPU idle

Stock Chromium on a Pi 4 decodes H.264 in hardware, then redraws every frame on the GPU. At 1080p60 that shows about 48 of 60 frames. With two small patches to Chromium and three to wlroots, decoded frames go straight to the Pi's display hardware, and the GPU does no work for the video at all.

The ready-made Tenfoot image includes these builds. A manual install runs on stock Chromium until you add them.

| 1080p60 H.264 test clip | Stock | Patched |
| --- | --- | --- |
| Frames shown, of 60 | 47 to 55 | 58.2 to 59.4, 0 dropped |
| GPU jobs per second | about 175 | 0 |
| Chromium's GPU process, % of a core | 90 to 94 | 49 |

Measured on a Pi 4 (1.8 GB), Raspberry Pi OS Trixie, kernel 6.18, Mesa 26.2, cage 0.3.1, wlroots 0.20.2, on Chromium 154 and again on 155. GPU jobs and screen flips were counted from kernel trace events, frames from Chromium's own video statistics. As far as we could find, nobody had reported Chromium doing this on a Pi 4 under Wayland.

## Why it stuttered

The Pi 4 has two separate chips for pictures. The GPU (V3D) draws things. The display chip (the HVS) puts finished pictures on the screen, and it can scale a video frame and lay it over the page by itself, for free. Chromium ignored the display chip and had the GPU copy and redraw each frame into its picture of the page: one draw plus two tiled copies, 60 times a second.

It was not the decoder (Chromium was already using the V4L2 hardware decoder), and not the page's JavaScript.

## The five patches

Each removes one blocker on the direct path, and all five are needed together.

| Patch | Where | What was wrong | What it does |
| --- | --- | --- | --- |
| Chromium `0001` | `ui/ozone/platform/wayland/gpu/wayland_overlay_manager.cc` | Chromium refused to put a video on its own layer if it had a clipping box. Every video on a web page has one, even when it cuts nothing. | Refuses only a clipping box that really cuts into the video, as Chromium's ChromeOS display code already does. |
| Chromium `0002` | `ui/gfx/linux/gbm_wrapper.cc`, `wayland_surface_factory.cc` | Chromium asked Mesa "can you *create* NV12 buffers?" Mesa says no, so decoded frames never became layer-ready buffers. | Asks "can you *import* this one?" instead. Mesa can. |
| wlroots `0001` | `types/scene/wlr_scene.c` | Chromium puts an invisible 1-pixel layer under its window. cage counted it as something to draw, which blocked direct display. | Skips fully transparent 1-pixel layers. |
| wlroots `0002` | `types/scene/wlr_scene.c` | Once the video covered that layer, cage stopped sending it "frame done". Chromium waits for those, so the picture froze on the first frame. | Keeps sending them to a covered 1-pixel layer. It still isn't drawn. |
| wlroots `0003` | `backend/drm/atomic.c`, `libliftoff.c`, `render/egl.c` | The colour-range list was in the opposite order from the kernel's, so limited range went out as full: washed-out video. HD video without colour info was treated as SD (BT.601). | Fixes the order, and treats video of 720 lines or more as BT.709, like video players do. |

The colour-range bug was also in upstream wlroots when this was written (commit `dca0703d`, March 2026).

Three settings go with them, all already in `install.sh` and `system/kiosk.sh`: cage runs with `WLR_DRM_FORCE_LIBLIFTOFF=1` and the patched library, and Chromium with `--enable-features=WaylandOverlayDelegation` plus `--disable-gpu-memory-buffer-video-frames` (without that one, video decoded in software is put in buffers the Pi can't show as an overlay: a black picture with sound).

## Installing it

Only for a manual install; the image already has them. wlroots builds on the Pi in about a minute. Its build dependencies are listed in the script:

    sudo -u tenfoot -H sh -c 'cd ~/tenfoot && sh patches/wlroots/build.sh'

Chromium is cross-built on a big x86-64 Linux machine, about 3 hours on 24 cores and 47 GB (a Colab v5e runtime works; run it detached):

    bash patches/chromium/build.sh

Unpack the result in the repo on the Pi, then restart the kiosk:

    sudo -u tenfoot tar -I zstd -xf chromium-tenfoot.tar.zst -C /home/tenfoot/tenfoot
    sudo systemctl restart getty@tty1

To go back, delete `chromium/` and `wlroots-build/` from `/home/tenfoot/tenfoot` and restart the kiosk. Re-running `install.sh` keeps them.

**Security:** this browser gets no security updates by itself, and you are logging it into your accounts. Each Chromium release needs a rebuild and a new image (bump `V`, `RPT` and the checksums at the top of `build.sh`). To drop back to the system's Chromium, which does update, delete `chromium/` and `wlroots-build/` as above.

## What did not work

| Tried | What happened | Why |
| --- | --- | --- |
| Flag `WaylandOverlayDelegation` alone | Worse: 64% of frames dropped | Without the patches, cage had to draw the extra layer on the GPU. |
| `--use-gl=egl` | Software drawing, renderer at 221% CPU | Chromium fell back to drawing in software. |
| Chromium on Vulkan (ANGLE) | Pages drew, video was black | Not usable yet on the Pi's driver. |
| mpv `--vo=dmabuf-wayland` | Crashed under cage | |
| mpv `--vo=gpu --hwdec=v4l2m2m` | Blue screen, 60% dropped | The decoder's column (SAND) format can't be mapped that way. |
| wlroots debug switch to stop the freeze | Worked, but cage then drew hidden layers too | Too blunt; replaced by `0002`. |

## Limits

- **Protected video doesn't benefit.** Chromium decodes Widevine video in software on Linux, so Netflix, HBO Max and Disney+ still go through the GPU.
- **4K isn't realistic.** The Pi decodes 4K only in HEVC, and streaming sites use other formats.
- **YouTube may serve 60 fps uploads as 720p30** to the Pi. That's its own choice, and it isn't solved.
